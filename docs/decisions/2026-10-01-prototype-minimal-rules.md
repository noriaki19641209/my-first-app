# プロトタイプ実装用：最小限の仮ルール
記録日：2026-10-01  
対象：掛け算での初回実装に必要な、最小限の仮判定ルール

---

## 概要

実装前の監査で、以下が確認されました：

- **L1（基本フロー）**：実装可能 ✅
- **L2（支援フロー）**：仮ルールで実装可能 ⚠️
- **L3（終了・保留）**：試行後に決定 ❌

本ドキュメントは、L1+L2のプロトタイプを動かすために**絶対に必要な仮ルール**のみを整理します。

---

## 1. 診断の仮判定ルール

### 【最小限の判定カテゴリー】

```
診断結果を以下の3段階で分類：

✓（十分理解）
  ・正誤：正解
  ・説明：理由が述べられている（「5と2を足して7」など、数字と操作が両方出現）

?（部分的/不明）
  ・正誤：正解または誤答
  ・説明：理由の説明が不完全（「5と2だから」など、数字だけまたは操作だけ）

✗（理解していない）
  ・正誤：誤答または未回答
  ・説明：説明ができない、または「わかりません」
```

### 【実装時の判定基準】

| 診断観点 | 判定方法 | 実装例 |
|--------|--------|-------|
| **正誤** | 子どもの答え = 正解か | `if answer == correct_answer: correct = True` |
| **説明の質** | 理由説明に「数字」と「操作語」が両方あるか | `if '5' in explanation and '足' in explanation: detailed = True` |

### 【プロトタイプでの運用】

- 子どもの回答をそのまま記録
- 「詳細」「曖昧」の正確な線引きは試行後に決定
- 現在は「説明に数字と操作語の両方が含まれるか」で簡潔に判定

## 2. 支援選択の仮ルール

### 【最小限の判定ロジック】

```
診断結果 → 支援パス選択

【ステップ1】問題理解を確認
  IF 子どもが「問題が何を聞いているか」理解していない
    → ⑦-A（問題再設定）を選択

【ステップ2】概念理解を確認
  ELSE IF 子どもが「掛け算の意味」をわかっていない
    → ⑦-C（概念再構成）を選択

【ステップ3】計算精度を確認
  ELSE IF 子どもが「計算が不正確」
    → ⑦-B（計算指導）を選択

【デフォルト】
  ELSE → 支援不要（十分理解）
```

### 【実装時の判定表】

掛け算の例：

| 診断パターン | 選択支援 | 判定理由 |
|------------|--------|--------|
| 正誤✗、説明✗、回答「7個」 | ⑦-A | 「3+4」と足している → 「ずつ」が理解できていない |
| 正誤✓、説明？、回答「12個だけど『なぜ』かわかりません」 | ⑦-C | 計算はできるが概念が浅い |
| 正誤✗、説明✓（「3個ずつ4つ」と理由は言える）、回答「10個」 | ⑦-B | 「ずつ」は理解しているが計算ミス |
| 正誤✓、説明✓ | なし | 十分理解 |

## 3. 支援段階の仮ルール

### 【最小限の段階フロー】

```
各支援パス（⑦-A/B/C）での共通ルール：

段階1実行
  ↓
【判定】段階1で「正解が出たか」または「説明が改善したか」
  ├─YES → 支援終了（⑨へ）
  └─NO → 段階2へ
      ↓
    段階2実行
      ↓
    【判定】段階2で改善したか
      ├─YES → 支援終了（⑨へ）
      └─NO → 段階3へ
          ↓
        段階3実行
          ↓
        支援終了（⑨へ）
```

### 【「進展」の判定基準（段階内）】

**シンプルな判定：**

| 判定項目 | 進展の有無 |
|--------|----------|
| **正誤の変化** | 誤答→正解 = 進展 |
| **説明の改善** | 説明なし→説明あり = 進展 |
| **子どもの反応** | 「あ、そっか」などの気付き = 進展の可能性 |

**プロトタイプでの運用：**
- 上記のいずれか1つ以上が見られたら「進展あり」と判定
- 複数観点の重み付けは試行後に決定

## 4. 進展判定の仮ルール（⑨支援後の確認）

### 【最小限の3段階判定】

```
支援終了直後、簡潔な問い直し（子どもの同じレベルの別問題など）

【判定基準】

十分な進展：
  ・正解に至った
  ・かつ説明が改善している

部分的進展：
  ・正解には至っていない
  ・ただし「ちょっと改善した」痕跡がある
  （例：説明の途中に「ずつ」という言葉が出現など）

進展なし：
  ・支援前後で、改善が見られない
  ・相変わらず同じ間違いをしている
```

### 【実装時の判定フロー】

```python
def judge_progress_at_point9(before, after):
    """
    ⑨支援後の簡潔な進展判定
    before: 支援前の診断結果
    after: 支援直後の簡潔な問い直しの結果
    """
    
    # 判定1：正誤の改善
    correctness_improved = (before.correct == False and after.correct == True)
    
    # 判定2：説明の改善
    explanation_improved = (
        before.explanation_quality < after.explanation_quality
    )
    
    # 判定3：子どもの反応
    has_insight = "あ" in after.child_utterance or "ああ" in after.child_utterance
    
    # 統合判定
    if correctness_improved and explanation_improved:
        return "十分な進展"
    elif correctness_improved or explanation_improved or has_insight:
        return "部分的進展"
    else:
        return "進展なし"
```

## 5. 支援後の再診断（⑨→⑩'）の仮ルール

### 【最小限の流れ】

```
⑨支援後の確認で進展判定
  ↓
【進展あり（十分/部分的）の場合】
  ↓
⑩'再度⑥診断を実施
  ・診断項目：「正誤」「説明」のみ（シンプル版）
  ・複数観点は試行後に追加
  ↓
【⑩'の診断結果に基づいて】
  ├─十分理解 → ⑥'確認・称賛 → ⑧拡張問題へ
  └─部分的/不十分 → ⑥'確認・称賛 → ⑧拡張問題へ（ただし以下注記）
      注：「部分的理解のまま進む」ことが妥当かは、試行後に判定
```

### 【プロトタイプでの簡潔な実装】

- ⑨で「進展あり」なら、問答なしに⑩'診断を実施
- ⑩'の診断は「正誠」「説明」の2観点のみ（簡潔版）
- 試行後、診断観点を追加・精密化

## 6. これらのルールで実装できる範囲

### 【実装可能な部分】

✅ **L1（基本フロー全体）**
- ①問題提示
- ②思考時間（時間は仮に4秒など設定）
- ③回答受け取り
- ④正誤判定
- ⑤思考過程確認
- ⑥診断（3段階版）
- ⑥'確認・称賛

✅ **L2の骨格**
- ⑦支援パス選択（3ルール版）
- ⑦-A/B/C各段階の基本フロー
- ⑨支援後の確認（3段階判定）
- ⑩'再度診断（簡潔版）
- ⑧拡張問題への進行

✅ **掛け算の具体的教材**
- 複数バージョンの問題
- 各段階でのヒント文言
- 拡張問題のレベル化

### 【実装できない/試行後に決める部分】

❌ **L3（終了・保留判定）**
- 支援試行の何回目で終了するか
- 「別の支援パスを試す」のか「別単元へシフト」か
- これらは試行データ後に実装

❌ **診断の精密化**
- 「詳細」「曖昧」「？」の正確な境界値
- 複数観点の重み付け
- これらは試行後に決定

❌ **進展判定の精密化**
- 「複数観点を何個満たす必要があるか」
- 「安定性の測定」
- これらは試行後に決定

## 8. 引き渡し資料としての位置づけ

### 【本ドキュメントの用途】

このドキュメントは：
- ✅ プロトタイプ実装の仕様書として使用可能
- ✅ 実装チームへの最小限の引き渡し資料
- ✅ 試行前の暫定的な実装ルール

このドキュメントではない：
- ❌ 本番運用の最終仕様（試行後に決定）
- ❌ L3の正式な終了基準
- ❌ 診断・進展判定の確定値

### 【実装→試行→改善のサイクル】

```
【現在】プロトタイプ用の仮ルール ← 本ドキュメント
    ↓

    ↓
【試行】5～30人での段階的試行

    ↓

    ↓
```

## 最後に：本ドキュメントの位置づけ

本ドキュメントは：

**あくまでプロトタイプの仮ルール**

- 根拠のない正確さを追求しない
- 試行で修正することを前提に設計
- 「これが決まれば動く」という最小限のルールのみ

**試行後に大きく変わる可能性がある**

- 診断ルール → 試行後に精密化
- 進展判定 → 試行データで最適化
- 支援パス選択 → 子どもの実績で調整
- L3基準 → 試行後に初めて設計

実装チームは、本ドキュメントを「固定された仕様」ではなく「試行可能な初期設定」として扱ってください。
